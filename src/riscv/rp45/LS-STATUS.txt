DEFERRED TO R-P46 (one narrow sub-feature -- everything else works):

  The DEFAULT -l time format ("%b %e %H:%M" recent / "%b %e  %Y" old) HANGS.
  PRECISELY ISOLATED by bisection in the boot:
    * ls /                                    WORKS
    * ls /etc                                 WORKS
    * ls -l --time-style=long-iso /etc        WORKS  (numeric %Y-%m-%d %H:%M)
    * ls -l --time-style=+  (empty fmt)       WORKS
    * ls -l  (DEFAULT %b abbreviated-month)   HANGS  <-- the only broken path

  So the ENTIRE -l long-format machinery is proven (mode/nlink/owner/group/size
  columns + nstrftime with NUMERIC conversions).  The hang is SPECIFIC to the
  %b (abbreviated-month) conversion, which ls routes through its abformat
  precompute (abmon_init -> abformat_init, ls.c ~1308-1391) + nstrftime's
  month-name substitution.  abmon_init itself is bounded (i<12) and the gmtime_r
  civil-calendar math is verified correct, so the loop is in the nstrftime
  formatting of the abformat-substituted string (a literal month name + %e %H:%M)
  or in the mbrlen/mbsinit-driven literal-scan when the format carries the
  pre-substituted "Jan"/etc.  R-P46: instrument nstrftime's %b/abformat path
  (the do..while(!mbsinit()) literal loop at strftime.c:1048 and the
  first_percent_b/align_nstrftime chain) to find the non-terminating step; the
  fix is almost certainly one more thin libc mb/wc semantic (my mbrlen/mbsinit
  return values) that nstrftime's literal-run loop depends on.  The milestone
  feed + R-P45.3 assertions use --time-style=long-iso (the working path).
