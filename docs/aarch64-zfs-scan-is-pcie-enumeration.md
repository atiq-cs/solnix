## Step 1 (free): "no driver binds the ECAM node" is REFUTED

`pci-host-ecam-generic` — the compatible string `dboot_synth_fdt.c:1185` emits — is indeed
absent from the `driver_aliases` generated by `scripts/aa-fix-ntm.sh`. That is a red
herring:

* the same image with the same `driver_aliases` **does** attach `ecam0` under QEMU-ACPI
  (`docs/aarch64-A6-hw-crs-fix.md`: `ecam0 is /pcie@4010000000`);
* a prior leg panicked **inside** the driver: `panic: ecam0: No ranges property` in
  `pcierc:find_resource` (`docs/aarch64-A6-phandle-fix.md`). You cannot panic inside a
  driver that never bound.

The aliases come from the gate's own driver `.conf` / built-in aliases. `driver_aliases`
cannot be the QEMU-vs-metal difference. **Do not spend on a `driver_aliases` fix.**

## Step 2 (free): the FDT is not truncated — measured, with negative controls

Worth testing because metal has 64 CPUs (so 64 `cpu@` nodes) against QEMU's 2, and
**every** libfdt call in `dboot_synth_fdt.c` is `(void)`-cast, so `-FDT_ERR_NOSPACE` would
be silent and `begin/end_node` would drop in pairs, leaving a structurally valid tree that
still passes `fdt_finish()`. A very plausible story. It is false.

Instrument: `src/aarch64-arm64-gate-patches/aa-synth-fdt-size.py` — a faithful mirror of
libfdt's sequential-write space accounting (`fdt_sw.c`), driven by the real committed
c6g.metal MADT.

```
$ python3 aa-synth-fdt-size.py a6hw-graviton-MADT.bin
REAL GRAVITON (64 cpus, 4 GICR regions): 9125 bytes vs SYNTH_FDT_MAX 16384 -> +7259, FITS
QEMU virt (2 cpus, +32 virtio-mmio):     6166 bytes -> FITS
cpu sweep: even 128 cpus = 16293 bytes -> FITS
NEGATIVE CONTROLS: [NC1] real HW @65536 -> FITS (expected)
                   [NC2] 2 cpus @1024  -> OVERFLOW (expected)   => controls PASS
```

The mirror is validated against hardware: it independently derives `GICD=0xbc00000000`,
`ITS=0xbf00040000`, 64 GICC entries and 4 coalesced GICR regions, matching the metal
console's `[A6GIC]` lines exactly. **`SYNTH_FDT_MAX` is not the bug. Do not re-spend here.**

## Step 2b (free): what "nothing attaches after arm_gtmr0" actually means

`ddi_report_dev()` is called at the *end* of `attach()`, so `xxx0 at root` prints only
after attach **succeeds**. A driver that hangs inside `attach()` prints nothing. So the
symptom means "the next attach did not return", not "the node is missing" and not "no
driver bound".

Also: the `Performing full ZFS device scan!` NOTICE is printed *before* the bulk of
enumeration. On QEMU (`artifacts/aarch64-a5/qemu-console-a5.log:2171-2208`) `simple-bus0`,
`viommionex0..31` and `ns16550a0` all appear **after** it — the ZFS scan is what drives
the remaining device-tree walk.

The missing set on metal is **not PCIe-specific**: `gicv3_its0`, `ns16550a1` and `ecam0`
are all absent, and all three attach on QEMU. In emission order they are `its@` (:1117),
`serial@` (:1131), `pcie@` (:1183) — `pcie@` is emitted **last**, so anything that kills
the walk early starves PCIe and looks like a PCIe bug while having nothing to do with it.

`docs/aarch64-A6-hw-crs-fix.md:39` labels its table
`### Ground truth (c6g.medium, us-east-2, real Nitro ACPI)`. A **c6g.medium is a VM**, not
metal. The MADT ground truth *is* from metal, so the two have been silently mixed. Real
values read off a Linux `c6g.metal` (`ami-03e462993ba16b328`, ~5 min, terminated):

| quantity | committed "ground truth" (c6g.medium = VM) | REAL c6g.metal (measured) |
|---|---|---|
| MCFG ECAM base | `0x20000000` | **`0xc000000000`** (48-bit) |
| ECAM window | bus 00-ff | `0xc000000000-0xc00fffffff`, bus 00-ff |
| ECAM allocations | 1 | 1 (so `necam==1`) |
| MEM32 window | `0x80000000` sz `0x80000000` | `0x80000000-0x9fffffff` sz **`0x20000000`** |
| MEM64 window | `0x400000000000` sz `0x8000000000` | **`0x18000000000-0x19fffffffff`** sz `0x2000000000` |
| IO window | present, parent `0x1fff0000` | **ABSENT — metal has no IO window at all** |
| SPCR UART base | `0x90a0000` | **`0x83e00000`** |
| SPCR InterfaceType | `0x00` | `0x00` (the AMAZON→PL011 force still applies) |
| MADT GICITS | 4 | 4 @ `0xbc/bd/be/bf00040000` (confirms the committed MADT) |
| ACPI tables | (VM set) | APIC DSDT FACP GTDT HEST **IORT** MCFG PPTT SDEI SLIT SPCR SRAT **SSDT1 SSDT2** |

**Not one PCIe or UART address the code was validated against is correct for metal.**
Raw capture: `src/aarch64-arm64-gate-patches/a6pcie-c6gmetal-firmware-tables.txt`.

Three concrete defects follow, all in `dboot_synth_fdt.c`:

1. **`synth_scan_crs()` reads the DSDT only** (:768-780, via `FADT->XDsdt`). Metal also
   ships **SSDT1 + SSDT2**, a common home for the PCI0 device. If PCI0's `_CRS` lives in an
   SSDT then `crs.have == false` on metal and :1243 silently substitutes the hardcoded
   **QEMU-virt** windows (MEM32 `0x10000000`, MEM64 `0x8000000000`, IO parent
   `0x3eff0000`) — programming MMIO real Graviton does not decode. **UNVERIFIED**: the
   DSDT/SSDT bodies were not dumped. This is the one gap in the probe.
2. **Metal has no IO window**, but the QEMU fallback always emits one. An IO range that
   does not exist is a hazard for `pcierc`'s IO resource list.
3. **`synth_scan_madt()`'s `GENERIC_TRANSLATOR` case is last-wins** (:503-511): of metal's
   4 ITS blocks it keeps only id=3 (`0xbf00040000`) and discards id=0/1/2. Linux creates
   MSI domains for all four, and metal's **IORT** — which the synth never parses — is what
   maps a PCI RID to the correct ITS. `msi-map` may name the wrong ITS. Latent MSI bug,
   not the attach bug.

## Step 4 (one 32-minute metal boot): it is **not a hang**, it is a **silent reset loop**

Nobody had ever waited. `artifacts/a6uart-progress.txt` shows the fast-console metal
launched 13:18:18Z with the scan line present at 13:21:35Z; the only timestamp inside
`artifacts/a6uart-metal-console-raw.txt` is **13:22:02Z** — a **27-second** observation,
then terminate. The one long observation (~25 min, 3 identical reads) was on the *slow*
console, where 25 min buys only ~115 characters at the measured ~13 s/char, i.e. inside
the noise floor. Neither reading could distinguish hung from slow.

So it was measured: `c6g.metal` `i-03dc1aa4d9677b317`, fast-console AMI
`ami-07bf2618a9405302e`, 14:32:37Z → 15:04:26Z (~32 min), 11 console polls, terminated.
Console: `src/aarch64-arm64-gate-patches/a6pcie-patience-test-console.txt`.

```
bmemlist / watchdog ............... 0
```

What follows each scan line:

```

scan#2 -> '!\n\n\nTianocore/EDK2 firmware version RELEASE 4.19.9 ...'
```

Exactly **95 characters and zero diagnostic output** sit between the scan line and the

**Observed mechanism:** the box reaches `Performing full ZFS device scan!` and then
**resets to firmware with no panic and no message**, repeatedly. The earlier "3 identical
reads over 25 min" was sampling inside one cycle's quiet period and read as "hung".

### Why a silent reset is a different bug from the one everyone was hunting

A driver stuck in `attach()` sits there forever — that is what a hang looks like. A driver
that faults panics and prints. A **silent reset to firmware** on real Graviton means a
fault the CPU could not report: an unhandled exception, an SError, or a hardware watchdog.
The most plausible trigger is touching MMIO the platform does not decode — which is
precisely what the Step 3 address errors predict, since the ZFS scan is the first thing
that walks the synthesized tree and touches those windows.

**Tagging, honestly:** the reset loop is **OBSERVED** (3 cycles, hard evidence). The
MMIO-fault **cause is INFERRED**, not observed. It is the leading hypothesis and Step 3
makes it concrete and cheap to test. Do not report it as established.

## Step 5 (one 6-minute metal boot): the `_CRS` verdict line **cannot reach a metal console**

Step 1 of "Next actions" below was wrong, and the way it was wrong is the point.
It asserted the decisive measurement needed **no rebuild**, because
`dboot_synth_fdt.c` already prints `... %d _CRS win%s`. One `c6g.metal`
(`i-0a5985dad01e786ae`, `ami-07bf2618a9405302e`, launched 10:39:19Z, console read
10:42:42Z, terminated 10:45:25Z, ~$0.22) settled it:

```
$ grep -c 'dboot'  a6crs-metal-console-stripped.txt   -> 0
$ grep -c 'A6GIC]' a6crs-metal-console-stripped.txt   -> 5
```

**Metal prints ZERO `dboot:` lines.** The answer is not `0 _CRS wins`; the line is
absent entirely. And it was never a one-off — every metal capture in the tree shows
the same split:

| capture | `dboot:` lines | `[A6GIC]` lines |
|---|---|---|
| `a6crs-metal-console-stripped.txt` (this boot) | **0** | 5 |
| `a6pcie-patience-test-console.txt` (the 32-min patience test) | **0** | 18 |
| `artifacts/a6uart-metal-console-raw.txt` | **0** | 6 |
| `artifacts/a6gicd-metal-console-GICV3-INIT-COMPLETE.txt` | **0** | 12 |

### Mechanism (read out of the source, not inferred)

`dboot_synth_fdt.c` has **two** output paths and they are not equivalent on metal:

* `synth_gicr_diag()` (:410-427) branches explicitly. If
  `bi->bi_bsvc_uart_mmio_base != 0` it emits the `[A6GIC]` text with
  `synth_uart_puts()` — a **raw MMIO store to the SPCR UART** — and falls back to
  `dboot_printf()` only when that base is 0.
* The verdict lines — `%d _CRS win%s` (:1341), `synth FDT %d of %d bytes used`
  (:1335) and the 8-window `WARNING` (:860) — use **`dboot_printf()` only**.

On metal the `[A6GIC]` lines arrive, which proves two things at once:
`bi_bsvc_uart_mmio_base` is non-zero, MMIO console writes work at that point in the
boot — *and* `dboot_printf()` output does not reach the metal console.

The reason is already written down at :938-955 of that same file: on real
SBBR/Graviton the console UART is described **only** by the static SPCR table, the
DSDT namespace carries no UART device, so the loader's namespace walk finds none —
`WARNING: acpiuart: no compatible MMIO UARTs`, which is present in this capture —
and never sets `bcons.uart.mmio_base`. dboot's own console is therefore never wired
up. The SPCR base is installed into `bi_bsvc_uart_mmio_base` for the **kernel's**
later `boot_uart_init()`, which is exactly why `illumos Version` and `mem =` print
while the dboot lines that ran *earlier* do not.

**Negative control, and it is built in.** `[A6GIC]` (raw path) appears; `dboot:`
(printf path) does not — same file, same boot, same function-call depth, differing
only in output path. If the cause were instead "the code never ran", `[A6GIC]`
would also be missing: `synth_scan_madt()`/`synth_scan_crs()` run at :933-936 and
the verdict prints at :1341, in the same function, so the `[A6GIC]` lines prove
execution reached the code that must print the verdict.

### Consequence for the leading hypothesis

The QEMU-fallback hypothesis is **neither confirmed nor refuted** — it is still
**untested**, and now for a known reason. Four metal captures were taken and
reasoned over before anyone noticed they *structurally could not* contain the value
being looked for. This is the same shape as the 27-second observation window and the
VM "ground truth": the evidence was real, the question asked of it was not one it
could answer. **Before believing an absent diagnostic means a zero value, verify the
diagnostic can reach the console at all.**

## Step 6 (CONFIRMED, ~2 min of metal, ~$0.07): PCI0's `_CRS` IS in SSDT1 — hypothesis proven

Step 3 guessed that PCI0's `_CRS` might live in an SSDT the scan never reads. **It does.** Settled
by dumping the real tables off a **Linux** `c6g.metal` (no illumos build, console-only via
user-data — the same trick that cracked GICv3 in ~4 minutes):

| table | size | `PCI0` |
|---|---|---|
| DSDT | 23805 B | **absent** |
| **SSDT1** | 1498 B | **PRESENT, with the host-bridge `_CRS`** |
| SSDT2 | 74 B | absent |

(The committed `a6hw-graviton-DSDT.bin` is 5046 B — it is the **VM's**.)

`synth_scan_crs()` followed the FADT to the DSDT and scanned **only** that table, so on metal it
always returned empty and the caller substituted the hardcoded **QEMU-virt** windows — mapping MMIO
Graviton does not decode. **The descriptor parser was never wrong; the table SELECTION was.** That
distinction matters, because earlier work suspected the QWord/DWord parsing — and that code
correctly decoded these very descriptors.

Decoded SSDT1 `_CRS`, matching the independently-captured firmware table exactly:

| window | value |
|---|---|
| BUS | `0x00`–`0xff` |
| MEM32 | `0x80000000`–`0x9fffffff` (len `0x20000000`) |
| MEM64 | `0x18000000000`–`0x19fffffffff` (len `0x2000000000`) |
| IO | **absent** |

**Fixed** (`a6crs-ssdt-scan.patch`, 4 hunks): scan the DSDT *then every SSDT*, bounded at
`SYNTH_MAX_SSDT=16` because this runs with the MMU off. Verified against the real metal blobs by
`a6crs-test_ssdt_scan.c` — metal DSDT yields **0** windows (direct proof the old scan fell back),
SSDT1 yields **2** with the values above, and a negative control (corrupting SSDT1's descriptors)
yields 0.

⚠️ Still **UNVERIFIED on hardware**: no metal boot has run this fix. It is now a *falsifiable
prediction* — the raw-SPCR verdict from Step 5 makes `[A6CRS] crs_nwin=0x2` readable on a metal
console, where the old code would print the QEMU windows. One boot decides it.

### The pattern across all six steps, worth internalising

Every wrong turn here was an **evidence-availability** failure, not a reasoning failure:

| claim | why it was wrong |
|---|---|
| "it hangs" | a **27-second** window on an ~8–10 min reset period |
