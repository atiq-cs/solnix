# What the vendor DTB says — and why the payload cannot boot as built

Source: `/tmp/dts`, 9,083 lines dumped from the running vendor Linux 6.18.3 on the maintainer's board.
Every value below is **measured from the board**, not inferred.

## ✅ The console risk is CLOSED — we had it right

```
aliases { serial0 = "/soc/serial@d4017000"; }
chosen  { stdout-path = "serial0:115200"; }

serial@d4017000 {
    compatible = "spacemit,k1-uart", "intel,xscale-uart";
    reg = <0x00 0xd4017000 0x00 0x100>;
    reg-shift = <0x02>;
    reg-io-width = <0x04>;
};
```

| our assumption | measured | verdict |
|---|---|---|
| UART at `0xd4017000` | `0xd4017000` | ✅ |
| `reg-shift = 2` | `0x02` | ✅ |
| `reg-io-width = 4` (io32) | `0x04` | ✅ |
| baud 115200 | `serial0:115200` | ✅ |
| compatible in `ns16550_uart_compat[]` | `spacemit,k1-uart` **and** `intel,xscale-uart` — **both present** | ✅ |

So the console-bind fix's "UNVERIFIED-until-hardware" caveat is now **resolved**. The kernel will find this
UART. That was the single largest unknown and it landed in our favour.

## 🚫 THE BLOCKER: our kernel is linked below physical memory

```
memory@102000000 {
    reg = <0x01 0x2000000 0x07 0xfe000000>;
};
```

| | value |
|---|---|
| DRAM base | **`0x102000000`** (just above the 4 GiB line) |
| DRAM size | **`0x7fe000000` = 32.0 GiB** |
| DRAM end | `0x900000000` |
| **our link address** | **`0x80200000`** |
| inside DRAM? | **NO** |

`0x80200000` is the standard qemu-virt **and** K1 DRAM base — correct for both, and **wrong here**. On this
board there is **no memory at all below `0x102000000`**, so the kernel would be loaded into a hole and could
not execute a single instruction.

⚠️ This is why there is no image to hand over. It is also a *tenth* QEMU divergence in effect: QEMU's DRAM
starts at `0x80000000`, so every one of the 8/8 gates ran at an address this hardware does not have.

Our `k1.dts` claimed 2 GiB flat at `0x0`. Reality is 32 GiB starting above 4 GiB. Note `0x102000000` is
**not** 4 GiB exactly — it is 32 MiB past it, so a naive "link at 4 GiB" would also fail.

## Hart topology — 16 harts, two ISA variants

```
16 cpu@ nodes (cpu@0 .. cpu@15)
 8 x riscv,isa = "rv64imafdcv"
 8 x riscv,isa = "rv64imafdcvh"    <- +h, the hypervisor extension
16 x mmu-type = "riscv,sv39"
```

Better than feared. The `A100`/`X100` split differs **only** by the `h` extension; the base ISA (including
`v`) and the MMU are identical across all 16. So this is not a big.LITTLE problem for us — we use neither
`h` nor `v` — but it is still **16 harts, not 4 or 8**, and hart identity is this port's most fragile area
(bug #10 was an OpenSBI boot-hart lottery). `cpu_ncpu_online()` and the hart-slot logic need re-checking at
16.

## Interrupt controllers — APLIC, not just PLIC

```
clint@e081c000                    compatible = "riscv,clint0"
interrupt-controller@e0804000     compatible = "riscv,aplic"
```

We have a CLINT (good — timer and IPI work as expected), but the external interrupt controller is an
**APLIC**, not the `riscv,plic0` QEMU provides. Any PLIC-specific register work needs an APLIC path.

## Timebase — and a bug this exposes

```
timebase-frequency = <0x16e3600>   = 24,000,000 Hz = 24 MHz
```

⚠️ **`src/riscv/uts/timer.c:28` hardcodes QEMU's 10 MHz** ("qemu virt CLINT timebase: 10 MHz => 100 ns per
tick"). At 24 MHz every interval would be wrong by **2.4×** — the `nanosleep` measured as "169 ms for a
150 ms request" would become ~70 ms, and callouts would fire early. This must come from the DTB.

`asy_nsuart.c:599` already uses `24000000` for the UART clock, so the value was known in one file and
hardcoded wrongly in another.

## What this changes

The board is healthy, its firmware is readable, and **the hardest unknown (the UART) is confirmed correct**.
But three things must change before any boot attempt:

1. **Relink for DRAM at `0x102000000`** — a build-system change, not a guess.
2. **Read `timebase-frequency` from the DTB** instead of assuming 10 MHz.
3. **Generate `k3.dts` from this dump** rather than editing `k1.dts` by hand — 16 harts, the real memory
   map, APLIC, and the true peripheral set.

None of these needs the board. All three are verifiable in QEMU **only** for absence of regression — QEMU
cannot validate the load address, because its DRAM is at a different place. That is precisely the divergence
that has bitten nine times.

All three are now done: `riscv.ld` takes `KBASE`/`KDRAM_BASE`, `timer.c` reads the timebase via
`fdt_get_timebase()`, and `k3.dts` is generated by `src/riscv/uts/gen-k3-dts.py`. Two further blockers were
found while doing so, both below.

## 🚫 A FOURTH BLOCKER: there is no SD-card boot path on this board

Found while building the payload. It changes the deliverable rather than adding work. Every value measured
from `/tmp/dts` and `/tmp/dixr-system.txt`:

```
mmc@d4280000   compatible = "spacemit,k3-sdhci";  status = "disabled";
mmc@d4280800   compatible = "spacemit,k3-sdhci";  status = "disabled";
mmc@d4281000   compatible = "spacemit,k3-sdhci";  status = "disabled";

ufshc@0xc0e00000  compatible = "spacemit,k3-ufshcd";  status = "okay";

/chosen/bootargs: ... boot_mode=nor ...
  mtdparts=d420c000.spi:128K@0(bootinfo),512K@128K(fsbl),64K@640K(env),
           1M@704K(esos),384K@1728K(opensbi),-@2112K(uboot)
```

And `lsblk` shows no `mmcblk` at all: `sda` 119.3 G (`sda2` = `/boot`, `sda3` = `/`) plus seven `mtdblock`
devices — exactly the six `mtdparts` partitions plus the whole-chip device.

| | |
|---|---|
| all three SD/MMC controllers | **disabled** |
| root device | **UFS**, not a card |
| boot chain | **SPI NOR** (`boot_mode=nor`) |

So **an SD image would boot nothing**, and shipping one would violate this repo's own rule that a stale
flashable image is worse than none. The K1 flow's `solnix-k1-sd.img` has no K3 analog and should not get one.

**The replacement vehicle is safer, not weaker.** The board already mounts `/boot` (sda2) from its own
running Linux, so: copy `unix-k3.Image` + `k3.dtb` there, interrupt the vendor U-Boot, `booti`. That leaves
the BootROM → FSBL → OpenSBI → U-Boot chain in NOR **completely untouched**, so recovery from any failure is a
power cycle — a failed attempt cannot brick the board. This also retires the eMMC/NOR-recoverability argument
that motivated the SD route in the first place.

Full procedure: `docs/k3-first-boot-runbook.md`.

## 🚫 A FIFTH FINDING: the Image header's `text_offset` was absolute

Not in the original list, and it would have shipped a kernel that loads at the wrong address even with a
correct `KBASE`.

U-Boot's `booti_setup()` (`arch/riscv/lib/image.c`) relocates to `gd->ram_base + text_offset`. `riscv.ld`
emitted `_image_text_offset = BASE` — the **absolute** link address:

| platform | `gd->ram_base` | absolute `text_offset` | relocates to | correct? |
|---|---|---|---|---|
| qemu virt | `0x0` | `0x80200000` | `0x80200000` | ✅ accidentally |
| SpacemiT K1 | `0x0` | `0x02000000` | `0x02000000` | ✅ accidentally |
| **SpacemiT K3** | **`0x102000000`** | `0x102200000` | **`0x204200000`** | ❌ ~4 GiB too high |

Fixed as `TEXT_OFFSET = BASE - DRAM_BASE`, with `DRAM_BASE` from a new `--defsym KDRAM_BASE=` defaulting to
`0`, so the qemu and K1 links stay byte-identical and only the K3 path changes. Verified by sabotage: with the
absolute form reinstated, `build-k3-payload.sh` reports `booti would relocate to 0x204200000, kernel linked at
0x102200000`.

⚠️ **`image_header.S` already documented the assumption it rested on**: "text_offset must equal the address
riscv.ld linked the image at ... and K1's `gd->ram_base` is `0x0`". The comment was correct and the code was
correct — *for the K1*. The premise silently stopped holding when a second board appeared. Same shape as
`riscv.ld`'s DRAM comment asserting K1 DRAM at `0x0..0x80000000`. The general hazard worth naming: **correct
code resting on a documented premise that later stopped being true**. Both comments are now corrected, not
just the values.

This is the **eleventh** QEMU-vs-metal divergence, and it shares a mechanism with the tenth: QEMU's
`gd->ram_base` is `0`, so QEMU can validate neither the load address nor the `text_offset`. Both bugs passed
8/8 gates for exactly the same reason.

## A sixth thing, fixed: `MAXCPU` 8 was not merely "too small" at 16 harts

`main.c` had `MAXCPU 8` and clamped an out-of-range boot hartid to `0`:

```c
startup_boot_hartid = (int)(boot_cpu.bc_hartid < MAXCPU ? boot_cpu.bc_hartid : 0);
```

On a 16-hart board that fold **deterministically reinstates bug #9**. If OpenSBI boots on hart 8..15, the boot
hart takes slot 0 while `start_secondaries` — which skips only `h == boot_hartid` — releases the real hart 0 as
a secondary into `dispatch_init_cpu(0)`, and two harts share one slot. On the K3 that is **half the harts**,
not a one-in-three lottery.

`MAXCPU` is now 16 in `main.c` and `proc.c`, `secondary_stacks` in `locore.S` holds 15 stacks, and the fold is
gone: an out-of-range boot hart now prints a panic naming the three files to change rather than silently
aliasing. `hart-slot-check.py` also read only 8 slots, so it could not have seen an alias involving a high
hart at all; it now reads `MAXCPU`.

Measured with `dispatch_init_cpu(0)` reinstated at `-smp 16`: `ALIASED=4 NOBOOT=2 SKIP=2`, with boot harts 7,
8, 9 and 15 caught. On the clean tree, 10 runs gave `CLEAN=3 NOBOOT=1 SKIP=6` and **zero** aliased. And the
sabotaged kernel **still passed the scanout gate** — a fresh confirmation that crash rate is a useless control
here and the precondition is the only thing worth checking.
